# Conatus 桌面 AI 工作台产品化可行性调研

- 日期：2026-10-30
- 状态：决策稿（阶段 0 未开工）
- 范围：评估将 Conatus 产品化为桌面 AI Agent 工作台的技术可行性、产品定位、实现路线与投入风险
- 项目边界：**只使用 Conatus；Nava 不参与本项目，不作为依赖、应用壳或验证环境**
- 技术路线：Flutter 桌面壳 + React UI + Conatus Dart 运行时（Dart 逻辑跨端复用，UI 每端单写，见 7.6）
- 本文只做调研与决策建议，不包含实现代码

> 本文合并自同日两版初稿。第二版相对第一版的唯一实质变化是「Nava 不参与」，该变化已传导至
> 能力核查、架构分层、工期与验证方案；第一版中关于 Nava 能力的观察改写为设计参照，见 4.3。

## 一、结论摘要

**技术上可行，但不建议直接开发一个通用版 WorkBuddy。**

1. 以 Conatus 为运行时开发本地桌面 Agent 工作台，Agent Loop、会话、模型、MCP、Skills 和定时任务等底层能力可以复用，技术上成立。
2. Nava 不参与后，其终端 UI、工作区管理与 Checkpoint / Undo 应用层不可复用；文本 diff 已抽成共享包 `conatus_diff`，文件工具正在上提为 `conatus_fs_tools`，Checkpoint 仍只在 Nava 内、未抽包。
3. 缺口不止桌面 UI：办公工具与产物管线、文件变更保护、操作系统级隔离、桌面发布工程，以及一层把运行时装配成办公能力的应用服务层，都需要新建。
4. 正面复制 WorkBuddy 的专家团、技能市场、IM 遥控、连接器与团队协作，不适合独立开发者现阶段投入。
5. 通用「WorkBuddy 替代品」的商业定位偏弱；更值得验证的是：**本地优先、过程可回溯、文件级可撤销的个人 AI 工作台。**
6. 不建议立即投入桌面 UI。应先用本项目自己的最小任务运行器验证三条办公任务链，达到可靠性与产物质量门槛后，再进入桌面 Alpha。
7. 阶段 0 的结论比 UI 更早决定产品是否成立；任务链不稳时，UI 只是掩盖问题。

## 二、关键决策：Nava 不参与

这条决定改变了本文其余所有估算，因此单独记录。

**决策**：本项目只依赖 Conatus 框架，不复用 Nava 的任何应用层代码。

**依据**（可核对的事实）：

- Nava 是终端编码智能体，应用层围绕 TUI、代码工作区与编码工具链构建（`conatus_code/lib/src` 下的 `tui`、`tabs`、`coding`、`lsp`、`lint` 等），服务对象是编码场景。
- 它有独立仓库、独立版本与独立二进制发布（`dist/nava`），演进节奏由编码产品决定。
- 本项目目标是桌面办公工作台。以 Nava 为壳，办公能力会被绑到编码产品的形态与发布周期上。

**代价**：应用服务层——工作区、办公工具装配、产物管理、变更保护——从零建设（文件工具实现可复用上提的 `conatus_fs_tools`，装配与策略仍需自建）；阶段 1 工期由 10–14 周上调到 14–20 周，本文按 20 周做计划。

**复议条件**：若阶段 0 证明主要瓶颈在工具装配而非运行时，且 Nava 应用层已稳定，可重新评估**抽取共用层**，不是整体复用。

**不随决策改变的部分**：Nava 在 checkpoint、diff、revert、story、permissions 上的设计取舍仍是本项目最好的参照，见 4.3。

## 三、WorkBuddy 产品形态拆解

WorkBuddy 官方将其定义为面向办公场景的 AI Agent 桌面工作站：用户用自然语言交代任务，系统自主规划与执行，并交付可验证的结果。其能力包括文档、表格、演示文稿、数据分析、本地文件处理及手机端远程任务下发。[^1]

其国内产品页进一步强调多专家、多模型、Skills、MCP，以及策略到交付的一站式执行。[^2]

因此，这类产品不是一个 Agent Loop，而是五层组合：

| 层 | 核心职责 |
|---|---|
| Agent 运行时 | 规划、模型调用、工具执行、多轮循环、失败恢复 |
| 任务工作台 | 任务列表、过程展示、中断、继续、恢复、并行任务 |
| 产物系统 | 文档、表格、PPT、图表的生成、预览、变更检查与交付 |
| 能力生态 | Skills、MCP、专家、连接器、定时自动化 |
| 安全与产品工程 | 权限、隔离、账号、安装、升级、跨平台与诊断 |

Conatus 强在运行时和部分生态。由于 Nava 不参与，终端应用已实现的产品能力不能计入复用范围；缺口因此不止桌面 UI，还包括运行时与完整办公产品之间整层应用服务。

## 四、Conatus 现有能力核查

本次核查基于 Fi2zz/conatus 当前仓库内容，而非历史设计。[^3]

Conatus 是 27 个模块包组成的 Dart monorepo，另有 `conatus_code` 子模块（不参与本项目）。根包为纯 Dart，Flutter 可直接使用。

### 4.1 能力映射

| WorkBuddy 能力 | Conatus 现状 | 本项目判断 |
|---|---|---|
| 自然语言任务、自主规划 | Agent Loop、Plan、Reflection | 可直接复用 |
| 多模型与模型回退 | OpenAI 兼容 Provider、Anthropic、回退链与重试 | 可复用，需自行做产品配置界面 |
| 本地文件批处理 | FS / Shell 能力缝与本地实现 | 需自行装配办公文件工具与工作区规则 |
| 任务中断与恢复 | Session、Task Center、任务取消与持久化 | 可复用 |
| 执行过程追踪 | Session Log 记录模型请求、响应与工具轨迹 | 数据层可复用，追踪界面自建 |
| 文件变更检查与撤销 | 文本 diff 有 `conatus_diff`；文件工具正上提 `conatus_fs_tools`；Checkpoint 仅 Nava 产品级实现（会话 / 轮次级），未抽包 | diff 与文件工具复用；Checkpoint 与撤销需自建，见 7.3 |
| 文档补丁与人机双写 | `conatus_doc` 提供实验性补丁内核 | 后续研究，非首版成熟能力 |
| Skills / MCP | 已有，兼容现有技能与 MCP 生态 | 可复用 |
| 定时自动化 | Cron、Schedule | 可复用 |
| 子 Agent / 多 Agent | 已有，Team 仍属实验性 | 首版慎用 |
| 浏览器操作 | `conatus_browser_use` 的实验性 provider 抽象 | 可验证，非成熟集成 |
| 原生桌面软件操作 | `conatus_computer_use` 的实验性 provider 抽象 | 首版排除 |
| DOCX / XLSX / PPTX 生成与预览 | 无 | 主要缺口 |
| 图形桌面工作台 | 无应用 UI | 需新建 |
| 凭据管理 | 能力缝齐全（env / 内存 / 文件 / Vault / AWS） | 缺 macOS Keychain 实现，见 4.4 |
| IM 遥控、账号、连接器市场 | 无 | 后置 |
| 安装、升级、跨平台验证 | 框架不负责桌面应用发布 | 需新建 |

### 4.2 两个不能混淆的概念

**第一，`conatus_doc` 不是 Office 文档生成器。** 它是人机双写故事层的文档补丁引擎，负责补丁、fold、supersede、批注与历史分叉，不负责 DOCX、XLSX 或 PPTX 的生成和渲染。

**第二，工具审批不等于沙箱。** Conatus 提供工具风险分级与审批，但本地 Shell 默认以当前用户权限执行。审批决定「是否允许调用」，不能在进程启动后限制其文件、网络和系统访问。WorkBuddy 官方权限说明同样把「高危操作确认」与「额外沙箱保护」分开描述。[^4]

因此安全隔离是公开提供给非技术用户之前的 P0 问题，不是后续优化项。

### 4.3 事实修正与设计参照

初稿里有三处表述需要收紧，否则会误导后续估算：

- **多模型能力**：实际是 `OpenAiCompatibleProvider` + `Anthropic` + 回退链 + 重试，没有 Kimi 专用适配。Kimi 等模型走 OpenAI 兼容层即可，但不应表述为「已支持」。
- **浏览器与桌面操作**：仓库里是实验性 provider 抽象（`browser_use` / `computer_use` 各自带 `providers/` 目录），具体接哪个实现、成熟度如何，需要在阶段 0 复核，不能当作成熟集成计入复用。
- **「纯 Dart 可直接在 Flutter 进程中使用」**：成立，但分发方式会反过来约束运行时能力（见 7.5，阶段 2 决策）。

**Nava 的设计参照**（应用层代码不可复用，设计可借鉴；diff 计算已由共享包承担）：

- 变更前快照 + 分阶段确认（`checkpoint`，会话 / 轮次级，仅 Nava 内实现）。
- 差异呈现优先于直接覆盖（呈现与确认在应用层，计算由 `conatus_diff` 承担）。
- 撤销本身可能失败，因此有补偿式回滚（`revert_compensate`），并把「撤销失败」当成一等状态处理。
- 权限规则与只读路径分离（`permissions`、`read_only_paths`）。

这几点直接决定本项目变更保护模块的形态，见 7.3。

### 4.4 能力缺口（按缺口量化）

| 缺口 | 现状 | 影响 |
|---|---|---|
| 办公产物 | 全仓无 xlsx / docx / pptx 支持；PDF 需选库；CSV 只有上下文压缩器，没有解析与生成 | 阶段 0 必须先定选型 |
| 桌面凭据 | `conatus_credentials` 无 Keychain 源 | BYOK 在 macOS 上的正确落点缺失，需新增一个 source |
| 变更保护 | diff 内核与文件工具正在上提；Checkpoint 只有 Nava 内实现，未抽包 | 阶段 0/1 需自建最小版（快照、任务边界、撤销） |
| 隔离 | 无操作系统级沙箱 | 阶段 2 公开分发前补齐；阶段 0/1 以工作区限制兜底 |
| UI 与桌面工程 | 无窗口、菜单、文件选择器、通知、升级 | 阶段 1 主体工作量；分发与升级属阶段 2 |
| 评估 | Session Log 有轨迹，没有评估字段（任务 ID、产物路径、是否人工修改、耗时、成本） | 阶段 0 的验收无法量化 |

## 五、产品定位建议

### 5.1 不建议的定位

不建议以「国产 WorkBuddy 替代品」或「全场景 AI 办公桌」为定位：

- 大厂已具备开箱即用、专家模板、模型与生态整合优势。
- BYOK、本地文件、多模型本身不足以形成长期差异。
- Agent 框架技术先进不是普通用户愿意付费的直接理由。
- 独立开发者需要长期承担模型适配、格式兼容、安全责任与桌面支持成本。

### 5.2 建议验证的定位

> **本地优先、过程可回溯、文件级可撤销的个人 AI 工作台。**

核心价值不是「也能聊天和调用工具」，而是：

- 每一次执行都能复盘。
- 每一批文件变更都能检查。
- 出错时可以连会话与文件一起退回。
- 用户保有模型、技能、数据与凭据的控制权。

Conatus 的 Session Log 为「过程可回溯」提供数据基础；Diff、Checkpoint、Undo 必须在本项目中新建。定位可以保留，但不能把待建能力描述为现状。

这一定位是否足以支撑付费仍需真实用户验证。企业私有部署可能有预算，但会同步提高沙箱、权限、审计与技术支持成本，不作为首版假设。

## 六、首版产品边界

### 6.1 建议纳入

- macOS 优先。
- 单窗口、单工作区、单 Agent。
- Ask / Plan / Execute 三类任务状态。
- 网络调研、本地文件整理、CSV 数据分析。
- 输出 Markdown、HTML、PDF、CSV。
- DOCX / XLSX 作为第二批产物能力。
- 任务过程、文件变更、产物列表和预览。
- 会话恢复，以及新建的 Checkpoint / Undo 最小实现。
- BYOK、MCP、Skills。

### 6.2 明确不做

- Computer Use。
- 多 Agent 专家团。
- 技能市场。
- 微信、飞书等 IM 遥控。
- 企业账号、云同步和团队协作。
- Windows 首版适配。
- 「任何任务都能完成」的泛化承诺。

首版承诺收窄为：**在用户授权的文件夹内，完成若干类可验收的文件工作。**

## 七、技术架构

桌面 UI 采用 Flutter 承载窗口与系统集成，React 承载工作台界面。推荐结构：

```text
React
├─ 任务与会话界面
├─ 对话、计划、工具过程
├─ 权限确认、设置
└─ 产物列表与预览
        │ JSON-RPC 命令 + 事件流
Flutter Desktop
├─ 窗口、菜单、文件选择器
├─ React WebView 容器
├─ 本地桥接与权限控制
└─ 安装、升级、平台集成
        │ Dart 直接调用
本项目应用服务层
├─ 工作区与文件工具装配
├─ 产物管理、预览与变更保护
├─ 桌面任务、权限和设置
└─ Checkpoint / Diff / Undo
        │
Conatus Runtime
├─ Agent Loop、Task、Session
├─ MCP、Skills、Cron
├─ FS / Shell / Approval 能力缝
└─ 模型、成本与执行日志
```

Flutter 官方支持编译为原生 Windows、macOS 和 Linux 桌面应用；Conatus 为纯 Dart，可直接在 Flutter 进程中使用，不需要另起 JS 运行时。[^5]

### 7.1 职责划分

**React**：工作台、会话、任务列表；对话与计划展示；工具执行时间线；产物列表、Diff、Markdown / HTML 预览；设置与权限确认界面。

**Flutter**：桌面窗口、系统菜单、原生文件选择器；本地通知、拖放、快捷键；React 本地资源加载与桥接；Conatus 生命周期、安装与升级。

**应用服务层**（Nava 不参与后必须明确新增的一层）：把 Conatus 的 FS、Shell、Approval 装配成办公工具；管理工作区、授权目录、任务配置与模型配置；管理办公产物、预览、文件变更与导出；实现 Checkpoint、Diff、Undo；向 React 提供稳定 ViewModel，不直接暴露框架内部对象。

**Conatus**：Agent Loop、任务、会话与执行日志；MCP、Skills、Cron、模型与工具执行；FS / Shell / 审批能力缝；Agent 状态的底层事实来源。

### 7.2 桥接原则

桥接只分两类通信：

1. **命令**：创建任务、发送消息、取消任务、批准操作、恢复会话、撤销变更。
2. **事件**：模型增量、计划更新、工具进度、审批请求、产物变化、任务结束。

传输结构化 ViewModel 与文件引用，不反复传输整份 Session Log 或大文件正文。大文件通过受控本地资源协议按需读取。

**状态权威只在 Dart 侧。** React 只保存输入框、选中标签等界面状态，不推导任务状态，不在 JS 侧再实现一套 Agent Loop。

### 7.3 文件变更保护（Checkpoint / Diff / Undo）

这层是本项目差异化的载体，现状却是「一半已有、一半要建」：

- **diff 计算**：`conatus_diff` 已落地（实验性零依赖：统一 diff 生成 / 解析、行级 LCS、hunk 应用），Nava 与本项目共用，本项目不重写算法。
- **文件工具**：正在从 Nava 上提为 `conatus_fs_tools`（`read` / `write` / `edit` / `list` / `glob` / `grep` / `apply_patch`），本项目直接复用，不再自建一套。
- **Checkpoint**：目前只有 Nava 的产品级实现，粒度是**会话 / 轮次**的工作区文件时间旅行。本轮提取不含它，父仓的 `conatus_checkpoint` 只是候选（可选包），尚未立项。因此阶段 0 / 1 按「自建最小实现」估算；若该包后续落地再替换。
- **粒度先对齐**：现有实现锚在会话 / 轮次，而本产品的执行单元是任务（Ask / Plan / Execute）。若要「按任务撤销」，自建时需加一层任务分组；也可以接受轮次粒度，换取与 Nava 语义一致。
- **撤销机制**：文件写入、移动、删除仍经应用服务层的 FS 适配器走 Conatus 的 `EffectScope` 登记，按 LIFO 回滚，幂等、迟到登记安全、抗异常。

「撤销可能失败」是一等状态：回滚失败的步骤要报告到具体文件，并保留可重试路径（参照 Nava 的 `revert_compensate`）。

### 7.4 WebView 安全约束

- 生产环境加载本地 React 构建产物，不依赖开发服务器。
- 不开放任意 JavaScript 执行与远程调试。
- 所有桥接命令做来源、参数和权限校验。
- 普通网页内容不得获得原生桥接能力。
- React 不直接访问文件系统，文件操作仍经应用服务层与 Conatus 权限管线。
- 首版不做 React 与 Flutter 混合嵌套界面，避免两套导航与交互体系。

### 7.5 macOS 分发（阶段 2 决策）

分发与安装升级不在阶段 0 / 1 的范围内，本阶段只做验证。现在只需守住一条约束，避免把架构定死：

- **不假设 Mac App Store 分发。** App Sandbox 下任意子进程执行基本不可用，而 Shell 是 Agent 的核心能力；按 App Store 设计等于直接砍掉核心能力。
- 阶段 2 再定分发方式（预期是 Developer ID 签名 + 公证的站外渠道），届时一并处理 security-scoped bookmark、升级通道与诊断。
- 「工作区限制」不依赖系统沙箱兜底，而是在应用服务层强制（路径校验 + 只读区域 + 审批阈值）。这条与分发方式无关，阶段 0 就要做。

### 7.6 React 与 Flutter 的分工

UI 用 React 是决定，不是待验证的假设。理由不是「将来复用到 Web」，而是 React 的界面生态成熟度：工作台布局、虚拟列表、diff 视图、Markdown / HTML 预览、表单与状态管理都有现成方案，自研同等成熟度不划算。

跨端复用落在 Dart 侧：Agent 运行时、应用服务层、产物与变更保护都是纯 Dart，可被不同 UI 复用；**UI 每端单独一套**，不为共享 UI 引入跨端 UI 框架。

代价与约束（验收项，不是实现细节）：WebView 桥接协议与事件重放、React / Dart 的异常与取消语义对齐、WKWebView / WebView2 差异、本地资源打包与 CSP，见 7.2 与 7.4。

## 八、候选路线比较

| 路线 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 直接使用 WorkBuddy | 最低成本获得办公自动化能力 | 没有自研产品价值 | 适合使用，不适合达成产品化目标 |
| 基于 Eigent 等开源桌面 Cowork 改造 | 较快获得完整桌面形态 | Conatus 容易被边缘化，变成集成项目 | 可作竞品与实现参考，不作首选底座 |
| Conatus + Flutter + React | 保留自研运行时与差异化；React UI 生态成熟 | 需自建应用服务、桥接、预览与桌面工程 | **推荐产品路线** |
| 先做本项目最小任务运行器 | 无桌面 UI 负担，直接验证 Conatus 办公任务链 | 仍需实现最少工具装配与产物输出 | **推荐验证顺序的第一步** |

Eigent 是 Apache-2.0 的开源 Cowork Desktop，可用于对照多 Agent 工作台与桌面交互，但选择它会显著改变本项目以 Conatus 为核心的目标。[^6]

浏览器自动化继续走 Playwright MCP；确有原生软件操作需求时再接 Cua Driver，它提供 MCP 接口并支持 macOS、Windows、Linux，首版无需自研桌面控制协议。[^7]

## 九、工作量估算

以一名开发者、只复用 Conatus、不使用 Nava 为口径：

| 阶段 | 目标 | 工作量区间 |
|---|---|---:|
| 阶段 0 | 本项目最小任务运行器，跑通三条办公任务链 | 2–4 周 |
| 阶段 1 | macOS 桌面个人 Alpha，含最小应用服务层 | 14–20 周 |
| 阶段 2 | 稳定产物、安全、安装包和评估后公开测试 | 再增加 4–8 个月 |
| WorkBuddy 全功能对齐 | 专家生态、连接器、IM、企业能力 | 不建议按此立项 |

口径说明：

- 阶段 0 的 2 周下限，以「产物管线选型已定」且「三条任务链已写成可执行任务卡」为前提；两项未完成时按 4 周估。
- 阶段 1 按 20 周做计划、14 周当冲刺目标。差额主要来自变更保护、桥接与预览的不确定性。分发与安装升级不计入阶段 1。

React + Flutter 增加的主要成本：WebView 桥接协议与事件重放；React / Dart 的异常、取消、断线语义对齐；WKWebView / WebView2 差异；本地资源打包、CSP 与桥接口白名单；跨层集成测试。

最大的进度浮动项不是聊天页面，而是：

1. DOCX / XLSX / PPTX 的生成质量与预览。
2. 长任务失败恢复。
3. 工作区规则、文件变更保护与系统隔离。
4. 不同模型上的任务成功率。

分发、签名与升级通道属阶段 2，不参与阶段 1 的浮动项评估。

## 十、主要风险与对策

| 风险 | 影响 | 建议 |
|---|---|---|
| 通用产品定位过大 | 长期追赶大厂功能，无法形成差异 | 锁定可回溯、可撤销、本地文件交付 |
| 低估应用服务层 | 有运行时和 UI，仍不构成完整产品 | 单列工作区、工具装配、产物与变更保护模块 |
| Agent 任务可靠性不足 | UI 完整但产物不可用 | 先用最小运行器验证，再做桌面 UI |
| 无操作系统级沙箱 | 非技术用户可能遭受越权或数据损失 | 阶段 0/1 限制工作区；阶段 2 公开分发前补隔离 |
| macOS 分发与沙箱冲突 | 按 App Store 分发会让 Shell 能力不可用 | 阶段 2 决策；在那之前不假设 App Store 方案 |
| Office 生成与预览复杂 | 工作量失控、产物质量不稳定 | 首版 Markdown / HTML / PDF / CSV，Office 分批 |
| React / Dart 双状态 | 界面与真实执行状态不一致 | Dart 为唯一状态权威，React 只消费投影 |
| 实验性能力过早产品化 | API 变更与故障增加 | Team、Browser Use、Computer Use 不进首版核心 |
| 商业价值未验证 | 投入数月但没有付费需求 | 先做真实使用与付费意愿门槛 |

## 十一、验证方案（阶段 0）

在本项目内实现一个不含 React / Flutter 的最小任务运行器，直接装配 Conatus、办公文件工具与产物输出，执行 30 个真实任务：

1. 调研主题并生成带引用的报告。
2. 分析 CSV / Excel 并生成图表和结论。
3. 批量整理授权文件夹并生成变更清单。

该运行器是本项目的技术验证代码，不是另一个终端产品，也不依赖 Nava。

**验收门槛**（五条硬指标 + 一条主观确认）：

- 至少 80% 的任务无需人工救场完成。「救场」定义为：人工修改产物、手工补步骤、重跑任务三者之一。
- 产物可直接交付，不需要大幅返工。
- 中断与恢复能正确工作。
- 文件变更可检查；撤销不造成二次数据损失。
- 没有越权写入或不可恢复的数据损失。
- 连续自用两周，确实比现成产品更符合自己的工作方式。

**度量要求**：每次运行产出一条结构化记录，至少含任务 ID、模型、耗时、token 与成本、产物路径、是否人工修改及修改内容、失败原因分类。Session Log 已有轨迹，评估字段需在阶段 0 补上——事后补不回来。

## 十二、阶段 0 前置条件

以下六项在开工前定清楚，否则阶段 0 的结论会被工具选型和口径问题污染：

1. **三条任务链的可执行定义**：每条的输入样例、授权目录、期望产物、验收判据。
2. **运行器形态**：命令还是库 + 脚本；任务如何声明；产物与运行记录落在哪里。
3. **产物管线选型**：PDF（纯 Dart 库或无头浏览器）、CSV 解析与图表、HTML 模板、XLSX 读写的候选库、许可证与维护状态。这是零依赖取向与产品需求的第一次正面冲突。
4. **变更保护的最小语义**：Checkpoint 粒度、存储位置、Undo 边界（撤文件不撤会话？）、撤销失败的呈现方式。
5. **评估口径落地**：第 11 节的结构化字段由谁写入、写到哪、如何汇总。
6. **工作区安全底线**：路径校验、只读区域、审批阈值三者的组合方式——阶段 0 就会真实写文件，这是唯一必须做对的安全项。

## 十三、最终建议

**建议进入低成本验证，不建议现在立完整桌面产品项目。**

推荐顺序：

1. 用本项目最小任务运行器验证三条办公任务链。
2. 固定产物格式与验收标准。
3. 完成工作区权限与文件变更保护；分发与隔离方案留到阶段 2。
4. 再开发 macOS 单窗口 Alpha（Flutter 桌面壳 + React UI）。
5. 依据真实使用率、任务成功率和付费意愿决定是否扩展为公开产品。

一句话概括：**Conatus 足以作为桌面 Agent 产品的运行时；Nava 不参与后，本项目需要自行补齐完整的办公应用服务层。首先要验证的是能否稳定交付文件成果，而不是能否做出 WorkBuddy 的界面。**
